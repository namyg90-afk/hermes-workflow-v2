# 4. 자연어 업무 자동화 실습

각 실습은 **입력 → 처리 → 결과 → 검증 → 반복 설정**까지 완료해야 합니다. 아래 문장은 실행 요청 예제이며 이 교재 작성 과정에서 실제 예약·발송을 생성한 것은 아닙니다.

## 업무 비서 역할 지정

> 너는 내 업무 비서야. 일정 정리, 자료 조사, 보고서와 뉴스레터 작성을 도와줘. 시작 전에 현재 작업 폴더와 사용할 수 있는 도구를 확인해줘. 결과에 사용한 출처, 확인 시점, 생성 파일, 미확인 사항을 남겨줘. 읽지 못한 자료는 읽은 것처럼 쓰지 마. 외부 발송은 내가 정한 대상과 범위에서만 진행해줘.

기관명·독자·문체·보관 폴더를 추가하면 같은 요청을 반복하기 편합니다.

## 실습 1. 날씨와 정기 알림

> Asia/Seoul 기준으로 5분 뒤 광주 날씨를 확인해 이 Telegram 채팅에 한 번 알려줘. 조회 시각과 출처를 넣고, 예약 ID와 다음 실행 시각을 먼저 보여줘.

실제 도착을 확인한 다음 반복을 설정합니다.

> 평일 오전 9시에 오늘 광주 날씨와 준비물을 알려줘. 같은 목적의 기존 예약이 있으면 갱신하고 중복으로 만들지 마. 예약 ID, 시간대, 다음 실행 시각, 중단 방법을 알려줘.

완료 기준은 “알림을 설정하겠다”는 답변이 아니라 예약 저장 및 실제 도착 확인입니다.

## 실습 2. 지원사업 조사

> 우리 기관은 [지역], [업종], [기업 규모], [설립연도]이고 관심 분야는 [분야]야. 실행일 기준 접수 중인 지원사업을 기업마당·K-Startup·SMTECH·IRIS의 원문 공고에서 찾아줘. 공고명, 주관기관, 신청 자격, 마감일과 시각, 지원 내용, 원문 링크, 확인 시각을 표로 정리해줘. 자격이 불확실하면 확인 필요로 표시하고 우선 검토할 3개를 제안해줘.

출력 파일: `output/support-programs.md`. 원본 교재의 2026년 6월 공고 목록은 과거 실습 결과이므로 현재 모집 중 목록으로 재사용하지 않습니다. 조회 실패 시 공고를 만들어 채우지 않습니다.

## 실습 3. 뉴스레터 만들기

1. **자료 수집**: 기관 소식, 공개 기사, 사진 사용권, 독자를 정합니다.
2. **내용 확인**: 출처와 사실을 확인하고 기관의 실제 소식과 외부 뉴스를 구분합니다.
3. **본문 작성**: 제목·도입·핵심 소식·행동 요청·연락처를 구성합니다.
4. **웹 버전**: 모바일에서도 읽기 쉬운 HTML을 만듭니다.
5. **이메일 버전**: 메일에서 지원되는 단순한 구조로 변환하고 테스트 수신으로 확인합니다.

> input의 승인된 기관 소식과 최근 공개 복지 뉴스를 바탕으로 후원기관 담당자용 뉴스레터 초안을 만들어줘. 실제 기관 소식과 참고 뉴스를 구분하고 기사 링크와 날짜를 넣어줘. 3개 핵심 소식, 행사 안내, 후원 참여 링크를 포함해줘. 확인되지 않은 행사·성과·인용문은 만들지 마.

> 검토한 초안을 웹용 HTML과 이메일용 HTML 두 파일로 작성해줘. 이미지는 사용권이 확인된 자료를 쓰고 대체 텍스트를 넣어줘. 이메일 버전은 JavaScript 없이 단순한 레이아웃과 인라인 스타일로 구성해줘. 모바일 화면과 테스트 메일에서 제목·링크·이미지·줄바꿈을 확인해줘.

초안 완료와 발송 완료를 구분합니다. 발송 도구 연결, 수신자 목록, 발신자, 테스트 결과가 준비된 이후 지정된 범위로 발송합니다. 이미지 생성·이메일 도구는 언어모델 로그인과 별도 설정이 필요할 수 있습니다.

## 실습 4. 반복 업무를 스킬로 정리

> 방금 성공한 뉴스레터 제작 과정을 welfare-newsletter-builder 스킬로 정리해줘. 입력 자료, 실행 단계, 사실 검증, 파일명, 실패 시 처리, 발송 조건을 포함해줘. 새 자료로 한 번 더 실행해 절차가 재사용되는지 확인해줘.

스킬의 완료 기준:

- 필요한 입력이 빠졌을 때 무엇을 요청할지 정해져 있다.
- 리서치·초안·HTML·검토·발송 조건이 분명하다.
- 결과 파일과 출처가 연결된다.
- 다른 프로젝트의 데이터를 섞지 않는다.
- 실행한 에이전트에서 스킬이 발견되는지 확인한다.

스킬 설치 후에는 스킬 목록 또는 새 세션으로 인식 여부를 확인합니다. 모든 제품이 항상 전체 재시작을 요구하는 것은 아닙니다.

## 실습 5. GitHub Pages 배포

> 검토 완료된 공개용 HTML과 이미지 파일만 지정한 저장소에 올리고 GitHub Pages로 배포해줘. 배포 후 실제 주소를 열어 글·이미지·링크·모바일 화면을 확인해줘.

브랜치 기반 설정은 저장소 **Settings → Pages → Build and deployment → Source: Deploy from a branch → main / root 또는 docs → Save**입니다. 원본의 “Settings에서 Branch 선택”을 이 경로로 바로잡았습니다.

프로젝트 사이트 주소 예시:

```text
https://GITHUB_ID.github.io/REPOSITORY/FILE.html
```

코드 저장소에 업로드한 것과 Pages 배포가 성공한 것은 다릅니다. Pages 사용 가능 여부는 저장소 공개 범위와 계정 플랜에 따라 확인합니다. 서버 실행이나 비밀 API 키가 필요한 작업은 정적 페이지 안에 넣지 않습니다.

근거: [GitHub Pages 게시 소스 설정](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

## 실습 6. 연구·보고서 작업으로 확장

> 이 프로젝트의 입력 자료와 기존 결과를 확인하고, 작업별 데이터·코드·Figure·Table·문서 경로를 연결해줘. GPT가 초안과 통합을 맡고 필요한 부분은 agy의 Gemini 또는 Claude로 검토해줘. 사용 모델, 검토 원문, 채택 여부와 근거를 남겨줘. 핵심 해석은 내 결정 전까지 후보로 표시해줘.

Figure 검색은 확장자를 나눠 누락을 줄입니다.

```powershell
rg --files input output -g '*.png' -g '*.jpg' -g '*.jpeg'
rg --files input output -g '*.svg' -g '*.pdf' -g '*.tif' -g '*.tiff'
```

동일 그림의 버전·해상도·원본 데이터·생성 코드를 확인한 뒤 문서에 삽입합니다. DOCX의 생성과 렌더링 검증은 [설치 문서](01-install.md)의 도구 구분을 따릅니다.

## 운영 완료 기준

| 항목 | 남겨야 할 증거 |
|---|---|
| 예약 | ID, 시간대, 다음 실행 시각, 중단 방법 |
| 조사 | 원문 URL, 게시일, 조회일, 판단 근거 |
| 문서 | 결과 경로, 검토 결과, 미확인 사항 |
| 모델 검토 | 모델 ID, 입력 범위, 응답 원문, 채택 근거 |
| 배포·발송 | 실제 URL 또는 전송 결과, 대상, 확인 시각 |
| 장애 | 실패 단계, 오류 요약, 재시도 여부 |

같은 결과를 다시 보내지 않도록 완료 기록을 확인합니다. 반복 실패는 무한 재시도하지 않고 담당자에게 알립니다. 정상 운영 중 의미 없는 상태 알림은 줄이고 완료·오류·결정 필요 때 알립니다.
